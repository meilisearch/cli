# Contributing

This page gets you from a clone to a pull request. The conventions live in [`CLAUDE.md`](CLAUDE.md), the promises made to users in [`docs/contract/`](docs/contract/), and the contract wins over anything written here.

## Set up

Node 22 or newer, pnpm 11 (`corepack enable` installs it), Docker for the integration tests.

```sh
pnpm install
pnpm openapi   # the OpenAPI documents the tests read, into openapi/ (never committed)
```

The management document lives in a private repository: `pnpm openapi` needs `gh auth login` to fetch it. Without it you still get the Meilisearch API document, which is all Meilisearch API commands need.

## Run it

```sh
pnpm build                              # after every change
./bin/run.js --help

export MEILI_PROJECT_URL=http://localhost:7700
export MEILI_PROJECT_API_KEY=masterKey   # only if the instance has a master key
./bin/run.js get health                 # JSON: indented in a terminal, compact when piped
./bin/run.js get indexes --debug        # HTTP trace on stderr, keys masked
```

The management commands (not shipped yet) will read `MEILI_MANAGEMENT_TOKEN`, and `MEILI_MANAGEMENT_URL` to target something else than production.

`pnpm link --global` puts a `meili` command on your PATH that points at your checkout.

## Test

```sh
docker compose up -d   # Meilisearch on :7700 with the master key masterKey
pnpm test              # build, manifest, then unit, contract and integration tests
pnpm lint              # pnpm lint:fix applies the safe fixes
pnpm typecheck
```

- **Unit tests** mock HTTP with msw and snapshot the `--help` and the JSON output of each command.
- **Contract tests** keep the code and `docs/contract/` in sync. One of them failing after a code-only change means the doc needs the change too.
- **Integration tests** run the built binary against `localhost:7700`. They skip with a notice when nothing answers there, and are required in CI.

`pnpm test -u` updates the snapshots, only for an interface change you meant. One suite at a time: `pnpm exec vitest run --project unit`. Details in [`docs/contract/testing.md`](docs/contract/testing.md).

## Add a command

Run `/add-command get stats` with Claude Code, or follow "How to add a command" in `CLAUDE.md`. In short: one command per pull request, named after its API routes by the rules of [`docs/contract/commands.md`](docs/contract/commands.md), with a snapshot test, an integration test, the manifest regenerated by `pnpm gen:manifest`, and a changeset.

## Release

Every pull request that changes what the published package does adds a changeset, a small file in `.changeset/` with the version bump and one line for the changelog. A change to the docs of this repository, to the tests or to the CI needs none: a user of the package would not notice it. Help texts and error messages are code, a user sees them, so they do.

```md
---
"@meilisearch/cli": minor
---

Add `meili get stats --index <index>`.
```

The line names the command with its required flags; the optional ones live in `--help`. `patch` for a fix, `minor` for a new command or flag, `major` for a breaking change of the contract; before 1.0, `minor` too. Until the first release there is a single changeset, `.changeset/first-version.md`: add your line to it instead of creating a file.

Merging into `main` publishes nothing yet. The planned flow, with `changesets/action` in a release workflow: a "Version Packages" pull request bumps the version and writes `CHANGELOG.md` from the changesets, and merging it publishes `@meilisearch/cli` on npm, the only distribution channel, and tags the release. Until it exists, a maintainer runs `pnpm changeset version` and `pnpm changeset publish` by hand.
